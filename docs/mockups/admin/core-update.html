План обновления · по порядку

Whole planned-set: Core 1.8.0 → 1.9.0; Блог 1.4.2 → 1.5.0; Кабинет автора 1.0.0 → 1.1.0. Никакого сетевого подбора зависимостей или молчаливого обновления. Пример готового плана предполагает, что missing/modified Формы и FAQ уже восстановлены в exact version/digest и reconcile завершён; иначе старт блокируется.

  1. Проверить весь итоговый Core + SDK + modules + PHP/MySQL, конфликты и циклы; зафиксировать candidate digests, target versions, expected generation и plan hash.
  2. Проверить разрешения SystemAdmin, недавнюю аутентификацию и MFA именно для этого плана.
  3. Включить global maintenance, freeze writes; остановить и drain обычные cron-задачи и запросы.
  4. Сделать согласованную резервную копию БД + файлов с manifest; подтвердить доступность восстановления.
  5. Подготовить версии зависимостей: Блог 1.5.0 и Кабинет автора 1.1.0 перед переключением Core 1.9.0.
  6. Выполнить фиксированный migration graph: core/019_expand_routes → core/020_backfill_routes → core/021_switch_generation. Expand → bounded backfill/checkpoint → switch. Schema IDs не равны SemVer.
  7. Подготовить cache/routes/module map и проверить совместимость queued tasks/payloads; переключить одну pinned generation.
  8. Health check → снять maintenance и возобновить работу. Старые artifacts сохранить до drain/rollback window.

Nontransactional DDL: не откатывается общей SQL-транзакцией. Повторный runner сначала сверяет journal/checksums и фактическую schema; изменившийся план блокируется.

Ровно одна сохранённая предыдущая версия

Core · saved KNOWN previous slot: 1.7.0 · digest demo-prev… · generation 41.

Rollback — отдельное действие только к этому одному slot и coherent whole-set generation plan. Eligibility повторно проверяет зависимости, текущие schema/settings/task payloads, maintenance/freeze/drain. Старый ZIP/папка не являются rollback. Успешный update заменяет единственный slot прежним known current; failure/kill не стирает прежний slot. Pinned operation base сохраняется отдельно для recovery текущей операции, не второй selectable slot. Staging и draining directories не дополнительные версии для выбора.

Откат кода не восстанавливает backup и не отменяет несовместимые миграции. Если schema несовместима — rollback недоступен, требуется отдельное DB+files restore с RPO либо согласованный roll-forward.

Цепочка несовместимости

Target Core 1.9.0 → cms/blog >=1.5.0 (установлено 1.4.2) и cms/author >=1.1.0 (установлено 1.0.0; его manifest требует Core <1.9.0). Выберите совместимые targets всего набора; автообновления зависимостей нет.
